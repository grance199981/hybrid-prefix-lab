# E11：#65186 之后，粒度 64 下为什么有请求命中变少 / E11: why PR #65186 makes a few requests hit less at unit 64

## 问题

E7 R3 的四遍对比里，粒度 64 下装了 PR #65186 的版本（分支头 `e4ee672b`）每一遍有 27 个请求（0.8%）比它的合并基点（`2f70c32d`）少命中 64 到 1,344 个 token，两遍是同一批请求；默认配置下两边逐请求相同。#65186 已经合并进主线，所以这个现象现在在主线上。E11 问：原因是什么，影响有多大，是不是缺陷。

## 做法

只用 CPU，不重跑 GPU。

- **读规则。** 读 `2f70c32d` 的调度器切分规则（`_mamba_block_aligned_split`、`get_mamba_prefill_checkpoint_position`、`is_mamba_prefill_checkpoint_valid`）和 #65186 的改动。#65186 改过的测试写明，能在 kernel 里导出存档点的后端会跳过「prompt 最后一个块边界上的那次切分」，最后一段一次算完。
- **规则预测器**（`predict_hits.py`）：按切分规则模拟每一轮 prefill 分几段、每段结束时在哪里留下状态，一个请求的命中等于同一会话之前各轮留下的状态里、不超过共同前缀的最大位置。两个版本：基线（最后一段停在最后一个块边界和存档点上）和 PR（存档点有效时最后一段一次算完，只导出存档点那一份）。一次一个请求，不考虑淘汰。
- **第 1 步：** 在 E7 R3 的逐请求记录上，用预测器算两个版本的命中，和实测逐个对。
- **第 2 步：** 在 E1 的全部会话上（三个数据集、思考开和关、3 个种子）从头模拟两个版本，算受影响的请求占比、少命中多少，按 E2 量到的每 token 代价折成首个 token 的损失。
- 预测在动手前写下：预测器找出的正好是这 27 个；至少 25 个两边的命中都算对；两组对照（默认配置下找不出差别；基线也按 PR 的规则算时找不出差别）；E1 上受影响的不超过 3%，平均损失不到 PR 收益的十分之一。

## 结果

**第 1 步：E7 R3 的记录**（每遍 3,161 个第 2 轮起的请求）

| 运行 | 实测 PR 少命中 | 预测 PR 少命中 | 两边都有 | 基线命中预测准 | PR 命中预测准 |
|---|---|---|---|---|---|
| 粒度 64，第一遍 | 27 | 27 | 27 | 3,161 / 3,161 | 3,159 / 3,161 |
| 粒度 64，第二遍 | 27 | 27 | 27 | 3,161 / 3,161 | 3,159 / 3,161 |
| 默认配置 | 0 | 0 | 0 | 3,161 / 3,161 | 3,161 / 3,161 |
| 对照：基线也按 PR 的规则算 | 27 | 0 | 0 | 3,134 / 3,161 | 3,159 / 3,161 |
| 敏感度：每步预算 8,192 | 27 | 28 | 27 | 3,161 / 3,161 | 3,158 / 3,161 |

- 预测器找出的正好是这 27 个，没有多也没有少。PR 版本算错的 2 个是第一个会话的第 2 轮，576 上那份状态来自别的会话或对照请求，预测器不建模跨会话的命中。
- 两组对照都按预期：默认配置下找不出差别；基线也按 PR 的规则算时，一个差别也找不出来，基线的命中正好在这 27 个请求上算错。

**第 2 步：E1 的全部会话**（粒度 64，两个版本从头模拟）

| 数据集 | 第 2 轮起的请求 | PR 少命中的 | 占比 | 少命中的中位数 / 均值（token） | 摊到全部请求 |
|---|---|---|---|---|---|
| SWE-smith，思考关 | 5,370 | 122 | 2.27% | 576 / 650 | 14.8 |
| SWE-smith，思考开 | 5,370 | 39 | 0.73% | 384 / 556 | 4.0 |
| 对话，思考关 | 3,721 | 46 | 1.24% | 320 / 426 | 5.3 |
| 对话，思考开 | 3,721 | 13 | 0.35% | 320 / 399 | 1.4 |
| SWE-rebench，思考开 / 关 | 9,191 / 9,191 | 0 / 0 | 0 | — | 0 |

- 受影响的不超过 2.3%。摊到全部请求，最多每个请求少命中 14.8 个 token，按 4B 上每 token 约 0.08 毫秒折算约 1.2 毫秒；#65186 带来的收益是每个请求 20–43 毫秒。受影响的那 2% 每次多重算约 400–650 个 token，约 30–55 毫秒。

**结论**

- 原因：基线在 prompt 最后一个块边界（576 的倍数）上切一刀，顺带留下那里的状态；#65186 为了少停一步，最后一段一次算完，只存末尾的存档点。粒度 64 时存档点在块边界之后，块边界上的那份后备状态就没有了。下一轮在存档点之前就分叉时（上一轮 prompt 最后几个生成提示 token 跨过了一个 64 的格点），基线还能退回块边界，PR 只能退回上一轮的起点。粒度等于块大小（默认）时存档点就在块边界上，所以没有差别。
- 判断：这是 #65186 的设计代价，不是缺陷，影响远小于它的收益。根子是 issue #45238 那一族问题（存档点落在下一轮不会原样出现的 token 里），#65186 只是去掉了一个碰巧能兜底的后备。所以没有做修法，也没有单独报到上游。

## 局限

- 一个模型（Qwen3.5-4B，块 576），Triton/FLA 后端，一次一个请求，没有淘汰。FlashInfer 后端按代码应当有同样的行为，没有测。
- 预测器是规则的复刻，没有单独的单元测试；它的可信度来自上面的对照。每步预算按默认值 2,048 算（服务没有设 `--max-num-batched-tokens`）。
- 没有在 GPU 上直接看缓存里存了哪些状态（计划里的第 3 步），因为第 1 步已经逐请求对上了。

## 复现

预测器只用标准库：

```bash
# 第 1 步：在 E7 R3 的一次部署的记录上（四遍对比的 e1/ 记录），对比预测和实测
python experiments/e11_lost_block_state/predict_hits.py r3 <R3 记录目录> --cfg C1a --unit 64
python experiments/e11_lost_block_state/predict_hits.py r3 <R3 记录目录> --cfg C1a --unit 64 --same-rule   # 对照
# 第 2 步：在 E1 的回放记录上从头模拟两个版本
python experiments/e11_lost_block_state/predict_hits.py sim <E1 记录目录> --unit 64
```

逐请求记录没有放进仓库，汇总在 `results/`：`r3_C1a.json`、`r3_C1b.json`（第 1 步两遍）、`r3_C0a_default.json`（默认配置）、`r3_C1a_same_rule.json`（对照）、`r3_C1a_budget8192.json`（敏感度）、`e1_sim_unit64.json`、`e1_sim_default.json`（第 2 步）、`e1_hit_rates_by_unit.json`（按粒度 16、64 和默认算的 E1 命中率，见顶层 README「实际怎么设」）。
