# E12：修法 #61282 的代价、换并发和换模型、在当前主线上 / E12: the cost of PR #61282, other concurrency levels and models, and current main

## 问题

E10 查清了缓存吃紧时混合模型整段丢命中的原因，并验证了上游的修法 PR #61282（让每个请求一直持有 prompt 末尾那一块状态，请求结束时排在注意力块后面释放）。E12 问四件事：

- **A：修法有没有代价？** 它让每个运行中的请求在每个状态组里多持一块。缓存充足、吃紧有复用、吃紧没有复用三种情形下，首个 token、每 token 间隔、吞吐、抢占各变多少。
- **B：修法以后还剩的「只缺状态」是什么？** E10 第 4 步里真实会话上还剩 17 个和 9 个这样的请求。
- **C：在当前主线上还成立吗？** #61282 开了一个多月，主线的这两个文件改了很多。把它 rebase 到 2026-11-18 的主线 `191565a2` 再测。
- **D：只在 Qwen3.5-4B、16 个会话上成立吗？** 换 8 和 32 个会话、换 9B、换另一家的混合模型（IBM Granite 4.0，Mamba2）。

## 做法

一张 L40，Triton/FLA 后端，`--max-num-seqs 32`。负载和 E5、E10 相同：合成会话（S，16 个同时跑，12 轮，prompt 从 2,000 涨到 4,750 个 token）、真实 Agent 会话（L，SWE-smith，8 个 worker），A 另加一档没有复用的负载（U，每个请求一个新的 3,375 个 token 的 prompt，16 个同时跑，输出 256）。3 个种子。保留率 = 第 2 轮起命中等于无限缓存时命中的请求占比。每部分的预测和判据在开跑前写下。

- **A**（量耗时，卡上没有别人的进程）：主线和修法按「主线、修法、修法、主线」四段交错跑，每段 S、U、L 三种负载，记录钩子关。同一组两段的首个 token 中位数或吞吐相差超过 5% 的格子不下结论（对照）。`run_e12a.sh` 调 E10 的 `run_e10.sh`；`perf_table.py` 出每格的性能表，`a_judge.py` 做对照和比较。做了两次：第一次在 E10 的环境上（主线 `1479deb0` 和它的移植版），第二次（A'）在 C 的两个环境上，跑的时候另一张卡空着。
- **B**（只用 CPU）：`b_leftover.py` 用 E10 第 4 步修法组的钩子记录，看每个「只缺状态」的请求要的是哪一轮的存档点。
- **C**：用 E10 的 `fetch_sources.sh`（`OURS` 设成 `191565a2`）取三方合并的输入，`port_pr61282_main.py` 解四处冲突；PR 自带的测试文件按新的缓存接口改写（`port_pr61282_test_main.py`，只改建组的辅助函数，断言不变）。两个环境由 `scripts/setup/setup_env_main_191565a2.sh` 建：主线 `191565a2` 的 wheel，和只多这两个文件的 rebase 版。先过正确性对照（同一个 prompt 命中和不命中时，贪心解码的第一个 token 和 48 个 token 的文本相同），再跑 S 档四档池和 L 档三档池，记录钩子关（钩子是按旧接口写的）。
- **D**（量命中，和别人共用卡）：`run_e12d.sh` 按清单依次调 `run_e10.sh`，钩子开。新加的配置在 E5 的 `run_e5.sh` 里：`N1`（Qwen3.5-9B）、`G1`（`granite-4.0-h-micro`，36 层 Mamba2 加 4 层注意力，粒度 16）、`G0`（`granite-4.0-micro`，全注意力对照）。Granite 的池按 E10 的 CPU 回放算出的精确峰值定（见局限）。

## 结果

### C：当前主线上

rebase 有四处冲突：`single_type_kv_cache_manager.py` 一处（和 E10 的移植相同）；`kv_cache_coordinator.py` 三处，来自主线把 `free`、`pop_blocks_for_free` 改成接 `Request` 并先调 `cache_blocks_on_free`（#67053），解法是保留主线的接口和调用、放进 PR 的释放顺序循环里。PR 自带的 16 个测试改写后在主线上全部失败、在 rebase 版上全部通过；vLLM 自己的 `tests/v1/core` 离线跑，两边各 881 个通过，466 个因为拿不到测试模型的配置而失败，失败集合逐个相同。正确性对照两边各 9 组全部相同。

| 负载和池 | 主线 `191565a2` | rebase 版 | 抢占（主线 → 修法） |
|---|---|---|---|
| 合成会话，2,972 MiB（1.0 倍） | 0.010 / 0.010 | 0.084 / 0.060 | 0 / 174 → 0 / 207 |
| 合成会话，3,715 MiB（1.25 倍） | 0.045 / 0.045 | 0.519 / 0.281 | 0 / 42 → 0 / 114 |
| 合成会话，4,458 MiB（1.5 倍） | 0.256 / 0.056 | **0.984 / 0.846** | 0 / 0 → 0 / 36 |
| 合成会话，7,430 MiB（充足） | 1.000 / 1.000 | 1.000 / 1.000 | 0 → 0 |
| 真实会话，3,330 MiB | 0.282 | **0.847** | 0 → 15 |
| 真实会话，3,830 MiB | 0.683 | **0.962** | 0 → 0 |
| 真实会话，9,990 MiB | 1.002 | 1.002 | 0 → 0 |

合成会话斜线两边是输出 16 / 256 个 token，真实会话只有输出 16。缺陷在新主线上还在（主线已含 #67053，它修的是另一件事），同样倍数下主线丢得更多（旧主线 1.5 倍是 0.60 / 0.40）。rebase 版在真实会话上和旧主线上的移植版几乎相同（0.850 / 0.959）。预测「rebase 版 1.5 倍两种输出都不低于 0.95」只对了输出 16：池是按输出 16 的峰值定的，输出 256 时主线的最大占用约 4,340 MiB、修法约 5,210 MiB，所以 4,458 MiB 对输出 256 只有约 1.03 倍、低于修法自己的峰值（事后的解释，没有验证）。

### A：修法的代价

第二次（A'，新主线，另一张卡空着），8 格里 7 格对照通过：

| 负载和池 | 首个 token 中位数，毫秒（主线 → 修法） | 每 token 间隔，毫秒 | 吞吐，请求/秒 | 抢占 | 保留率 |
|---|---|---|---|---|---|
| 合成会话，充足，输出 16 | 258 → 261 | 56.5 → 56.8 | 12.10 → 11.99 | 0 → 0 | 1.000 → 1.000 |
| 合成会话，充足，输出 256 | 267 → 268 | 20.7 → 20.8 | 2.78 → 2.78 | 0 → 0 | 1.000 → 1.000 |
| 合成会话，1.5 倍，输出 16 | 3,620 → **270** | 212 → 60 | 2.90 → **10.93** | 0 → 0 | 0.257 → 0.984 |
| 合成会话，1.5 倍，输出 256 | 1,617 → **283** | 39.0 → 21.4 | 1.44 → **2.22** | 0 → 72 | 0.056 → 0.838 |
| 没有复用，4,458 MiB | 1,341 → **1,579（+18%）** | 39.4 → 40.7 | 1.411 → **1.306（−7.4%）** | 0 → **156** | — |
| 没有复用，2,972 MiB | 2,877 → 4,168 | 43.0 → 35.9 | 1.068 → 1.038 | 948 → 738 | — |
| 真实会话，3,830 MiB | 750 → **410** | 78.0 → 46.5 | 2.03 → **4.66** | 0 → 4 | 0.671 → 0.967 |
| 真实会话，3,330 MiB（对照没过，只当描述） | 4,337 → 545 | 227 → 62 | 1.18 → 3.13 | 0 → 29 | 0.289 → 0.859 |

- 缓存充足时两边相差不到 1.3%。有复用时修法的收益远大于代价：首个 token 降 45%–93%，吞吐升 54%–277%。
- 代价出现在「没有复用、缓存够主线用但不够多持的那几块」的那一档：吞吐 −7.4%，首个 token +18%，抢占 0 → 156 次。池再小（2,972 MiB），两边都在大量抢占，修法不比主线差多少。预测「池贴着时代价重现、稍大一档两边相同」反了过来：代价落在稍大的那一档。
- 第一次（A，旧主线的移植版，另一张卡上同时在跑 D）8 格只有 3 格对照通过，那一次只当描述；它量到同一类代价更大：3,456 MiB 没有复用时抢占 0 → 450、吞吐 −14%、首个 token +51%，5,184 MiB 时两边相同。「第一次的漂移来自另一张卡上同时跑的任务」是推断，第二次还换了代码和日期，没有单独隔离。

### B：修法以后还剩的

E10 第 4 步修法组里「只缺状态」的请求（3,330 MiB 上 17 个、3,830 MiB 上 9 个），**全部**要的是更早一轮的存档点（往前 2 轮的 14 个和 8 个，往前 3 到 5 轮的各 1 个），没有一个要的是上一轮的。修法只保护每个请求自己那一份状态；下一轮的 prompt 在上一轮的存档点之前就分叉时（比如上一轮的思考内容在历史里被去掉），要的那一份已经没有请求持有，照旧最先被淘汰。合成会话上修法组没有这样的请求。

### D：换并发、换模型（旧主线 `1479deb0` 上的移植版，输出 16）

| 配置 | 主线 1.0 倍 / 1.5 倍 | 修法 1.0 倍 / 1.5 倍 | 主线未命中里只缺状态 | 抢占（1.0 倍，主线 → 修法） |
|---|---|---|---|---|
| Qwen3.5-4B，8 个会话 | 0.007 / 0.868 | 0.425 / **1.000** | 1.5 倍 100% | 0 → 21 |
| Qwen3.5-4B，32 个会话 | 0.010 / 0.691 | 0.274 / **1.000** | 1.5 倍 100% | 0 → 0 |
| Qwen3.5-9B，16 个会话 | 0.000 / 0.108 | 0.079 / **1.000** | 1.5 倍 100% | 0 → 6 |
| `granite-4.0-h-micro`，16 个会话 | 0.902 / 1.000 | **1.000** / 1.000 | 1.0 倍 100% | 0 → 0 |
| `granite-4.0-micro`（全注意力） | 1.000（1.0 倍） | — | — | 0 |

- 换并发、换规模、换一家（Mamba2）都是同一个缺陷。Qwen3.5 一行的「只缺状态」按命中为 0 的请求算，Granite 按没命中满的请求算（输出 256 时是 99%）。9B 输出 256 时 1.0 倍上抢占 75 → 258。
- Granite 上轻得多，贴着峰值仍保住 84%–90%，1.5 倍就不丢；原因没有查。全注意力的 `granite-4.0-micro` 在自己的峰值上不丢。
- 代价随结构变：Granite 约有 9 个状态组（Qwen3.5 是 3 个），修法让它的峰值占用高 44%（307 → 442 块，CPU 回放算的）。这一次在 1.0 倍上体现成请求排队，没有抢占。

## 局限

- C、A' 只测了 Qwen3.5-4B；换并发、换模型测的是旧主线上的移植版。别家的混合模型只测了 Granite 一对。
- Granite 第一次跑时池按服务 `/metrics` 每秒采一次的占用定，采样漏掉了峰值（采到 137 块，CPU 回放算出 307 块，低估 2.2 倍），那一轮的四条预测因此不成立；结果在 `results/D3/`，照实保留。之后改用 CPU 回放的精确峰值（`results/D3/cpu_peak.txt`）重跑，结果在 `results/D3b/`。C 的池也是按采样的峰值定的，输出 256 那一格可能是同一个问题。
- A' 的对照 8 格过 7 格，没过的那一格只当描述。C 的耗时是两档负载同时在两张卡上跑时量的，只当参考。
- vLLM 自己的单元测试只能离线跑；要联网取模型配置的 466 个测试两边都失败。

## 复现

服务端的环境变量见 `run_e12a.sh`、`run_e12d.sh` 的开头，以及 E10 的 `run_e10.sh`、E5 的 `run_e5.sh`（`E5_MIN_TURNS=1` 加 `E5_TURNS=1` 是没有复用的负载；`HP_QWEN35_9B_DIR`、`HP_GRANITE_H_DIR`、`HP_GRANITE_DIR` 给新配置）。Granite 两个模型的下载清单在 `scripts/setup/manifests/granite-4.0-micro.json`。

```bash
# C：rebase
OURS=191565a2cd0c42a1e4fd4d063f53d0ce383b364f bash experiments/e10_state_eviction/fetch_sources.sh <dir>
python experiments/e12_fix_costs/port_pr61282_main.py <dir>        # 写 <dir>/port/，对照 port_pr61282_main.sha256
python experiments/e12_fix_costs/port_pr61282_test_main.py <PR 的测试文件> <输出文件>
# A、A'：每格的性能表和对照
python experiments/e12_fix_costs/perf_table.py <e5 目录>... --json out.json
python experiments/e12_fix_costs/a_judge.py <run_dir> --order "main191 pr191 pr191 main191" --json out.json
# B
python experiments/e12_fix_costs/b_leftover.py <修法组的 hook+e5 目录> --unit 16 --json out.json
# D：保留率和未命中分类用 E10 的 analyze_e10.py
```

汇总在 `results/`：`A/`、`A2/`（两次代价测量的逐格判定）、`C/`（新主线上的性能表）、`D12/`（换并发、9B）、`D3/`、`D3b/`（Granite 的两轮）、`b_leftover_pr61282_{L,S}.json`（B）。
